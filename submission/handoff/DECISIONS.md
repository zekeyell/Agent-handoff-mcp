S1 DECISION: UI depends only on the TaskRepository interface so Firebase can be swapped in WHY: Keeps persistence implementation separate from board behavior and enables Firebase to be added without coupling screens to its APIs. ALTERNATIVES: Have screens call Firebase directly, which would make storage changes ripple through the UI.
S2 DECISION: Use anonymous Firebase Authentication before starting the app WHY: The board has no account or sign-in UI, but Firestore rules must require an authenticated user. Anonymous auth satisfies that access boundary without changing the UI; users should be aware that data is tied to the anonymous Firebase account/device lifecycle. ALTERNATIVES: Public Firestore access is unsafe; adding interactive auth would require a UI change outside this task.
S2 DECISION: Store only title and status in task documents and use the Firestore document ID as Task.id WHY: This matches the existing model and allows rules to validate an exact, minimal field set. PLACEHOLDERS: Firebase options contain no real project credentials and must be regenerated with FlutterFire.
